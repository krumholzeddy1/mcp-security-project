**Task Unit 1.4 — Ethical Considerations**

Project: Detecting Tool-Poisoning Attacks in MCP Agentic Systems Using Machine-Learning-Based Anomaly Detection.

**1. Personal Data**

- No personal data is collected or stored. The project uses a locally hosted MCP testbed with synthetic tool descriptions and synthetic call-metadata logs generated specifically for this project, so anonymization is not required because no personal data exists in the first place.

- Only the data needed for the detection task is generated: tool-call metadata (call sequence, timing, description-change events) and labelled attack/benign status. No user identities, credentials, or real organizational data are used.

- No human participants are involved, so there is no requirement to inform or obtain consent from participants. If this changes (e.g., a later extension involves real SOC analysts reviewing detector output), a participant information sheet and consent form would be required and added as an appendix, with a corresponding ethics application.

**2. Mitigating Algorithm Bias**

- The training data is entirely synthetic and generated by the researcher, so the main bias risk is that the synthetic attack corpus over- or under-represents certain attack styles relative to real-world attacker behavior, effectively a coverage bias rather than a demographic one.

- Mitigation: synthetic scenarios will be grounded in documented, published attack patterns and CVEs (e.g., MCP tool-poisoning and rug-pull reports from Invariant Labs and academic MCP security literature) rather than invented ad hoc, and the benign/attack class balance will be checked and reported so any skew is visible and discussed as a limitation.

- The evaluation will report per-class metrics (precision/recall for both benign and attack classes), not only overall accuracy, so that any bias toward the majority class is detectable.

**3. Assessing Data Sources**

| **Question**                            | **Assessment**                                                                                                                                                                                                                                                                               |
|-----------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Was it ethically obtained?              | Yes — all reference material (CVE records, vendor security notices, published academic papers) is publicly published information intended for security-community consumption. The MCP client/server reference implementation used for the testbed is open source under a permissive license. |
| Does it contain the information needed? | The public CVE/vendor reports describe attack structure in sufficient detail to reconstruct representative (not identical) synthetic scenarios; no proprietary or restricted data is required.                                                                                               |

**4. Ethics, Legal, and Governance Across Regions**

- The project is conducted under University of Lancashire ethics guidance; because no personal data or human participants are involved, this is expected to qualify for a low risk / expedited ethics review, to be confirmed with the supervisor before testbed work begins.

- UK GDPR and the Data Protection Act 2018 apply to any data handling; as no personal data is processed, the primary relevant obligation is data minimization, which is satisfied by using only synthetic data.

- The MCP protocol and its reference implementations originate from organizations based in the United States (Anthropic) and, for context in the literature review, Google (for the A2A protocol, referenced but out of scope for implementation). No US data-protection regime is directly engaged since no personal or company data crosses borders, only publicly published technical documentation and open-source code are used.

- Responsible disclosure practice will be followed if any previously undocumented vulnerability is found incidentally during testbed development: it will be reported to the relevant maintainer and not published in the dissertation until resolved or explicitly cleared for disclosure.
