# Unit 2.4 — Data Collection

*Applied to: Detecting Tool-Poisoning Attacks in MCP Agentic Systems Using Machine-Learning-Based Anomaly Detection*

## 1. Alignment table (slide 4's template, applied directly)

The deck is explicit that data collection should be driven by the research question, not by what's convenient to obtain. Filling in the project's own version of the worked example:

| Element | This project |
|---|---|
| **Research Question** | To what extent can machine-learning-based anomaly detection of tool-call metadata and tool-description change patterns improve the detection of tool-poisoning attacks in MCP-based agentic systems, compared with existing schema-validation defences? |
| **Methodology** | Quantitative experimental research (confirmed in Unit 2.3) |
| **Data Required** | Labelled tool-call sessions (benign / poisoned / rug-pull), tool-call metadata features, model performance metrics (precision, recall, F1) |
| **Collection Strategy** | Synthetic data generation, grounded in documented attack patterns from secondary sources; feature engineering on metadata; dataset partitioning (train/test split) |

This maps cleanly onto the deck's own "Machine Learning" row (slide 6): labelled datasets, feature extraction, synthetic data — this project sits squarely in that category, not in Network Security (no real packet captures/IDS alerts) or Human-Centred Security (no participants, confirmed back in Unit 1.2).

## 2. Primary vs. secondary data — being precise about which is which

The deck draws a clean line between primary (generated for the project) and secondary (generated by a third party). This project actually uses both, and it's worth being explicit about where each one sits:

**Primary data:** the synthetic corpus itself (`data/corpus.csv`) — 600 labelled tool-call sessions generated specifically for this project.
- *Advantage realised:* full control over data quality and perfect alignment with the research question — every feature exists because the detector needs it, not because it happened to be in someone else's dataset.
- *Disadvantage realised:* this is exactly the same thing flagged in the critical analysis (Unit 2.2) — self-generated data risks reflecting the researcher's own assumptions about what an attack looks like, rather than the full diversity of real attacker behaviour. The deck's listed disadvantage ("time consuming, requires ethical approval") is only partly true here — no ethics burden since there's no personal data (per Unit 1.4), but the design-bias risk is real and already named.

**Secondary data:** the CVE reports, vendor security notices, and academic papers (Hou et al., Radosevich and Halloran, Invariant Labs, Willison, Bhatt et al.) used to *ground* the synthetic corpus design.
- *Advantage realised:* efficient, and lends real-world credibility to what would otherwise be an arbitrary synthetic design.
- *Disadvantage realised:* the deck notes secondary data "may not be aligned to your project goals" — accurate here too, since none of these sources publish raw tool-call metadata logs. They describe attacks in prose, not as structured data, so translating them into corpus features is an interpretive step the dissertation should document explicitly rather than presenting as a direct transcription.

## 3. Data quality — the honest version, against all five criteria

The deck names five: validity, reliability, accuracy, completeness, representativeness. This is the section worth taking most seriously, because it's where the corpus's actual weaknesses (already surfaced in Units 2.2/2.3) map onto a formal quality framework rather than sitting as informal caveats.

| Criterion | Deck's question | Honest answer for this project |
|---|---|---|
| **Validity** | Does the data measure what it's intended to measure? | Partially. It measures whether the detector can distinguish sessions with an embedded keyword-style marker from sessions without one. It does not yet measure detection of subtler, non-keyword-based poisoning, which is closer to what the research question actually asks about. This is the project's main validity gap. |
| **Reliability** | Can results be reproduced with the same methodology? | Yes — the generator uses a fixed random seed (`random.seed(42)`), so re-running `corpus.generate_corpus` produces an identical dataset. This is a genuine strength worth stating explicitly in the dissertation. |
| **Accuracy** | Is the dataset free from significant errors? | Not automatically — an actual error was caught and fixed during development: the baseline validator initially read the *post-mutation* description for rug-pull sessions instead of the registration-time one, which artificially inflated its detection rate to 100% and would have invalidated the entire comparison. This is worth including in the dissertation as a documented data-quality check, not hidden — it demonstrates exactly the kind of verification this unit is asking for. |
| **Completeness** | Are there enough observations for meaningful analysis? | 600 sessions (200 per class) is workable for a small tabular gradient-boosting model with 8–11 features, but modest. Worth stating as a scale appropriate to the timeline, not a data-rich study. |
| **Representativeness** | Does the dataset reflect the real population/environment? | This is the weakest criterion. Two specific gaps, both already identified in Units 2.2/2.3: (1) class balance is artificially even (200/200/200) when real MCP traffic would be overwhelmingly benign; (2) every attack contains an unambiguous keyword, which real attackers motivated to evade detection would not cooperate with. Both should be named directly in the dissertation's data section, with the skewed-balance and subtler-attack variants proposed in Unit 2.3 positioned as the fix. |

## 4. Best-practice self-audit (slide 14, answered honestly)

| Question | Answer |
|---|---|
| Does this data answer my research question? | Yes, with the validity caveat above — it answers a narrower version of the question (keyword-based poisoning) than the one stated. |
| Is the source reliable and well documented? | The generation code is documented and version-controlled; the secondary sources grounding it range from peer-reviewed to a single practitioner blog post (flagged in Unit 2.2) — mixed, not uniformly strong. |
| Have ethical and legal issues been addressed? | Yes — no personal data, no participants, confirmed in Unit 1.4. |
| Is the dataset sufficiently large and representative? | Large enough; not yet representative (see above). |
| Can another researcher reproduce my study? | Yes — fixed seed, version-controlled generation script, documented pipeline. |
| Have I documented my collection and preprocessing methods? | Partially — the code is documented; the dissertation's methodology chapter still needs to state these design decisions in prose, not just leave them in code comments. |

## 5. What this means for the next block of work

This unit doesn't change the plan so much as it gives the existing weaknesses a name and a place in the dissertation structure:

- The **accuracy** point (the baseline bug that was caught and fixed) belongs in the dissertation as evidence of rigour — it's a good story, not an embarrassing one, if written up honestly.
- The **representativeness** gaps are exactly what the skewed-class-balance and subtler-attack corpus variants (proposed in Unit 2.3) are for — this unit gives the formal justification for why that follow-up work is necessary, not optional polish.
- The dissertation's data section should state validity, reliability, accuracy, completeness, and representativeness as five explicit sub-headings, each answered as honestly as above — that structure alone demonstrates the critical, transparent practice this unit and Unit 2.2 are both asking for.
