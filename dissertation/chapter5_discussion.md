# Chapter 5: Discussion and Limitations

## 5.1 Interpreting the Main Finding

The central finding of this study is that a machine-learning classifier trained on tool-call metadata achieves an F1 score of 0.945 compared to 0.488 for a registration-time schema-validator — an absolute improvement of 0.457 F1 points driven almost entirely by the classifier's ability to detect rug-pull attacks that the baseline structurally cannot see. This result directly answers the research question in the affirmative: ML-based anomaly detection of call-time metadata and description-change patterns does improve detection of tool-poisoning attacks in MCP-based agentic systems, and the improvement is qualitative as well as quantitative.

The qualitative dimension is the more important one. The baseline's zero recall on rug-pulls is not a consequence of a poorly chosen threshold or an incomplete keyword list — it is an unavoidable consequence of the defender's observation window ending at registration. Adding more keywords, tightening the detection rule, or switching to a more sophisticated rule-based classifier would not change this outcome, because the attack-relevant signal (the description mutation) occurs after the baseline has finished looking. The ML detector's 88.1% rug-pull recall, by contrast, is achieved by monitoring features that are only observable after registration — principally `call_description_length` (54.5% feature importance) and `call_suspicious_keyword_hits` (34.0%) — neither of which is available to the baseline at all.

This confirms the mechanistic claim made in the research question: it is the *observability window*, not the sophistication of the detection logic, that is the binding constraint. Extending the window to include post-registration metadata is what enables detection of the rug-pull class, and the choice of gradient-boosted trees as the classifier architecture is secondary to that design decision.

## 5.2 The Stealthy Rug-Pull Bound and the Case for Continuous Monitoring

The ML detector's 8 false negatives — all from the stealthy rug-pull subtype — represent a hard theoretical limit on what any point-in-time metadata detector can achieve. A stealthy rug-pull is a session in which the server mutates its tool description and subsequently reverts it before the metadata snapshot used for feature extraction is recorded. At the moment of feature extraction, the description has returned to its clean registration-time value; `description_changed_after_registration` is zero, `call_description_length` equals `reg_description_length`, and `call_suspicious_keyword_hits` is zero. Every feature value is identical to that of a genuine benign session. No classifier, regardless of architecture or training data, can distinguish these sessions from benign on the basis of the eleven features used in this study, because the sessions are literally identical in the feature space.

The stealthy rug-pull is not a hypothetical edge case. An attacker with server-side control can easily implement a revert-on-demand mechanism: inject the poisoned description for a brief window during which the model's `tools/list` refresh would capture it, then revert. Any monitoring system that samples tool metadata at fixed intervals is vulnerable to attacks timed to fall between samples. This places a hard requirement on any detector intended to catch this subtype: the monitoring must be *continuous* rather than periodic, recording the description at every `tools/list` call and every tool invocation, rather than taking a single snapshot at a chosen checkpoint.

Implementing continuous monitoring changes the feature set substantially. Rather than a single pair of registration-time and call-time description values, a continuous monitor would track a time-series of description observations, enabling the detector to identify transient mutations — short windows in which the description deviates from its registration value and returns. The maximum deviation magnitude and duration, the temporal pattern of deviations, and the correlation between deviation windows and tool invocations would all become informative features. Developing and evaluating a continuous-monitoring detector is identified as the primary direction for future work (Section 6.3).

## 5.3 Limitations of the Synthetic Corpus

The most significant limitation of this study is that the evaluation corpus is entirely synthetic. While the synthetic approach is necessary given the absence of labelled real-world MCP attack data and the ethical constraints on capturing data from live deployments, it introduces several validity concerns that must be acknowledged.

**Distributional fidelity.** The five tool definitions in the testbed corpus (`get_weather`, `search_docs`, `create_ticket`, `send_notification`, `lookup_account`) are simple, short descriptions typical of minimal API documentation. Real-world MCP servers include tools with substantially more varied descriptions — some extremely terse, some multi-paragraph — and with domain-specific terminology that may interact unexpectedly with a feature set calibrated on the synthetic distribution. A detector trained on the synthetic corpus may therefore generalise poorly to real deployment environments without retraining on domain-appropriate data.

**Noise model conservatism.** The noise model applied in corpus generation (Chapter 3) was designed to prevent trivially separable classes while remaining within a plausible range of real-world variation. The specific rates chosen — 10% stealthy rug-pulls, 25% short fragments, 35% verbose benign descriptions — are not derived from empirical observation of real attack or benign populations; they reflect design judgements intended to produce credible rather than inflated evaluation results. A different set of rates would produce different evaluation figures. The rates are documented as named constants in the source code precisely to make this sensitivity transparent and reproducible, but the absence of empirical calibration means that the evaluation figures (F1 = 0.945 for ML, F1 = 0.488 for baseline) should be interpreted as illustrative of the relative capability difference rather than as precise estimates of real-world performance.

**Closed-world assumption.** The corpus contains three attack types and one benign type. Real deployments may exhibit attack patterns not represented in the training data — novel injection techniques, descriptions engineered to mimic benign length and entropy distributions, or attacks that operate through parameter schema fields rather than the description field (a vector noted by Radosevich and Halloran, 2025). A detector trained on the current corpus would have no basis for detecting these out-of-distribution attacks. Extending the corpus to cover a broader taxonomy of attack patterns, including schema-field injection and multi-tool coordinated attacks, is a necessary step before any real-world deployment.

## 5.4 Limitations of the Feature Set

**Keyword list completeness.** Two features — `reg_suspicious_keyword_hits` and `call_suspicious_keyword_hits` — depend on a fixed list of ten keyword patterns drawn from documented attack examples. The ML model's poisoned-session recall of 100% on the test set reflects the fact that the evasive fragments in the corpus, while designed to avoid the keyword list, still produce distinguishable length and entropy signals. In a real adversarial setting, a motivated attacker aware of the feature set could craft injection text that is simultaneously short enough to avoid a length threshold, composed of characters with entropy similar to benign descriptions, and free of any keyword on the list. The keyword features would contribute nothing against such an adversary, and the model's performance would degrade to relying entirely on the remaining nine features — most of which carry less than 5% importance in the current model.

**Description length as a proxy.** The dominance of `call_description_length` (54.5% importance) reflects the corpus design: attacks append text to a benign base description, making attacked descriptions longer on average. This creates a learnable signal, but it is also an easily defeated one: an attacker who constructs an injection fragment that replaces rather than augments the original description — producing a call-time length close to the registration-time length — removes the primary discriminating feature. The detector as currently designed is therefore better suited to detecting naive injection than sophisticated adversarial injection.

**Schema field injection.** The current feature set does not capture changes to the tool's parameter schema — field names, types, or required-field sets. Radosevich and Halloran (2025) demonstrate that injection via schema field names is effective because these fields appear in the model's context alongside the description. Extending the feature set to include `num_schema_fields` changes across the session, schema field name entropy, and schema mutation flags would address this gap.

## 5.5 Relationship to Existing Defences

The ML detector proposed in this study is best understood as a *complementary* layer in a defence-in-depth stack rather than a replacement for existing defences. The baseline schema-validator achieves 75.5% recall on poisoned sessions on the test set — capturing attacks that were registered with obvious injection keywords — at the cost of a single, lightweight string-matching operation at registration time. Removing it in favour of the ML detector would not be appropriate: it adds negligible overhead and catches a subset of attacks with very high precision (0.909).

The relationship to ETDI (Bhatt et al., 2025) is similarly complementary. ETDI's OAuth-based scope binding limits what an injected tool can accomplish, while the ML detector identifies that an injection has occurred. In a real deployment, ETDI would reduce the blast radius of any attack that the ML detector misses, and the ML detector would provide the signal needed to trigger remediation (session termination, server quarantine, human review) in cases where ETDI scope constraints cannot prevent the attack outright. Combining a registration-time integrity check (ETDI), a registration-time keyword screen (schema validator), and a post-registration behavioural monitor (the ML detector) provides coverage at three distinct points in the session lifecycle, with each layer catching what the others structurally cannot.

---

## 5.6 Summary

This chapter has argued that the ML detector's advantage over the baseline is mechanistically grounded in access to post-registration observability, and that the residual 11.9% false-negative rate on rug-pulls represents a theoretically motivated bound that can only be reduced by moving to continuous rather than point-in-time monitoring. The evaluation results are credible but should not be interpreted as estimates of real-world performance without retraining on domain-specific data. The feature set has known adversarial weaknesses — particularly against length-normalising injection and schema-field attacks — that define the scope of future work. The proposed detector is most usefully positioned as a post-registration monitoring layer within a layered defence stack, complementing rather than replacing existing registration-time controls.
