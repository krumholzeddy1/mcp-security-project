# Chapter 2: Literature Review

## 2.1 The Emergence of Agentic AI and Tool-Calling Architectures

Large language models (LLMs) have evolved rapidly from systems that respond to isolated prompts into autonomous agents that plan, reason across multiple steps, and invoke external tools to complete tasks on a user's behalf (Yao et al., 2023). This shift from passive responders to active agents has been accompanied by the development of standardised protocols that allow models to discover and call tools provided by remote servers — a capability that dramatically extends what an LLM can accomplish but also introduces a new and largely uncharted attack surface.

---

## 2.2 The Model Context Protocol

Anthropic's Model Context Protocol (MCP) has emerged as the dominant open standard for this tool-calling layer (Anthropic, 2024). MCP defines a message-passing interface through which a client connects to one or more servers, requests a list of available tools via a `tools/list` call, and subsequently invokes tools via `tools/call`. Each tool is described by a name, a free-text description, and a JSON Schema defining its input parameters.

Hou, Zhao, Wang, and Wang (2025) provide a comprehensive survey of MCP's design landscape and security implications. They identify a structural weakness that is central to this project: MCP was designed to solve an interoperability problem — enabling any client to communicate with any server using a common protocol — and treats security as a secondary concern. The protocol has no built-in mechanism for re-validating the trust placed in a tool after the initial connection is established. Each layer in the pipeline — user, model, client, server — is assumed to trust the layer immediately behind it, but nothing re-checks that trust once a session is running. Hou et al. (2025) argue that this creates a situation where a compromised or malicious component several hops downstream can inject behaviour that is, from the model's perspective, indistinguishable from a legitimate instruction originating from the user.

---

## 2.3 Tool-Poisoning Attacks

Tool poisoning exploits the model's reliance on tool metadata by embedding instruction-like text directly into the fields that the model treats as descriptive. Because LLMs are trained to follow instructions embedded in their context, text placed in a tool's name, description, or parameter schema can direct the model to perform actions that the user did not request and may not be aware of. This class of attack did not originate with MCP: Perez and Ribeiro (2022) established prompt injection as a general vulnerability of instruction-following language models — the observation that any text in the model's context window carrying imperative phrasing can override or redirect the model's behaviour. Greshake et al. (2023) extended this to *indirect* prompt injection, demonstrating that malicious instructions need not come from the user directly but can be embedded in any content the model reads, including external data sources and tool outputs. Tool poisoning via MCP metadata is a specific instantiation of this broader indirect-injection class: the injection vector is the tool description rather than a web page or document, but the underlying mechanism — the model processes the injected text as instruction rather than data — is the same. This class of vulnerability is catalogued as LLM01: Prompt Injection in the OWASP Top 10 for Large Language Model Applications (OWASP, 2025).

Invariant Labs (2025) published the first detailed public demonstration of tool poisoning as a practical attack against deployed MCP systems. Their report documents working exploits in which tool descriptions contain hidden directives — including instructions to exfiltrate local configuration files and relay session credentials to secondary endpoints — while the visible tool output remained unremarkable. As a commercial security vendor with a product in this space, Invariant Labs has an interest in establishing threat severity; their findings are treated here as corroborating evidence alongside the independently conducted audit of Radosevich and Halloran (2025).

## 2.4 The Rug-Pull Attack Pattern

A distinct variant that is more difficult to detect than direct poisoning is the delayed attack, commonly referred to as a rug-pull. Willison (2025) describes servers that register with honest, unmodified tool descriptions — passing any initial inspection or human review — and subsequently rewrite their tool definitions after the client has trusted them and established a session. From the protocol's perspective, nothing prevents a server from returning a different tool list in response to a `tools/list` call than it returned at the start of the session; the client has no mechanism for detecting or preventing this mutation.

Willison (2025) also identifies a related pattern: server impersonation, in which one server intercepts and responds on behalf of another server it was never meant to represent. Both patterns share the same structural property: the attack becomes visible only after the trust relationship has been established and the opportunity for initial inspection has passed. This places them outside the scope of any defence that checks a tool once, at the point of first registration.

Willison (2025) is a practitioner blog post, not a peer-reviewed study: it provides no methodology section, no prevalence data, and has not been externally verified. The rug-pull attack category in this dissertation's taxonomy therefore rests on a single non-peer-reviewed source — an asymmetry acknowledged in the methodology (Section 3.3.1) and limitations (Section 7.2). The Willison account is retained because the *mechanism* it describes — post-registration description mutation — is independently supported by Hou et al. (2025), who show that MCP's trust model structurally permits exactly this behaviour. The mechanism is grounded even if the empirical prevalence is not established.

## 2.5 Existing Defences and Their Limitations

Three categories of defence are in common use for MCP tool security, all of which share the structural limitation of checking a tool once rather than continuously. **Schema validation** inspects tool metadata at registration, catching malformed schemas but not injection embedded in well-formed description strings. **OAuth-based access control** (ETDI: Bhatt, Narajala, and Habler, 2025) extends MCP with cryptographically signed tool definitions and policy-based access scoping, limiting what a poisoned tool can accomplish — but does not address rug-pull attacks, because the injected instructions may fall within the originally approved scope. **Human review** is effective for short, readable descriptions but fails for subtle injection and provides no protection against post-registration mutations.

The common failure mode across all three defences is temporal: each checks tool metadata at a single point and does not revisit that check. Hou et al. (2025) characterise this as a structural property of MCP's trust model: the protocol provides no event notification when a server changes its tool definitions, and no session-level audit trail is maintained by the standard client.

## 2.6 Machine-Learning Approaches to Security Anomaly Detection and the Research Gap

The use of machine learning to detect security anomalies from behavioural metadata is well established in network intrusion detection and malware classification. Ahmed et al. (2025) survey a decade of ML-based intrusion detection systems and identify a consistent pattern: anomaly-based methods detect attack categories that signature-based methods miss by construction, because signatures require prior knowledge of the specific attack variant, whereas an anomaly model learns a representation of normal behaviour and flags deviations from it. Zhan et al. (2024) apply this principle to adversarial attacks against AI-enabled systems, demonstrating that metadata features — request timing, payload structure, response entropy — distinguish adversarial from benign queries even when inputs are crafted to evade input-level filters.

The application of this precedent to MCP requires a stated assumption: *the transfer hypothesis* — that the statistical regularities observed in network intrusion and adversarial AI detection will be reproduced when those methods are applied to MCP tool-call metadata. This is plausible given the structural similarity (detecting deviations from legitimate behaviour in session-level data) but is not a proven transfer; network packet metadata streams differ substantially in scale and resolution from MCP session snapshots. Sommer and Paxson (2010), in a widely cited critique of ML intrusion detection, argue that any anomaly detector trained on one dataset is brittle when faced with data from a different operational environment — the closed-world assumption — a concern directly applicable to a synthetic training corpus. This dissertation tests the transfer hypothesis empirically rather than assuming it holds.

No prior published work has applied ML anomaly detection to MCP tool-call metadata specifically to detect post-registration description changes. The closest adjacent work — Bhatt et al. (2025) and Hou et al. (2025) — analyses registration-time defences, leaving the post-registration detection problem unaddressed. The literature thereby establishes two complementary facts: rug-pull attacks are a documented, practical threat that exploits MCP's structural inability to re-verify trust after session establishment (Willison, 2025; Hou et al., 2025); and all deployed defences check tool metadata at a single point and are therefore structurally unable to detect post-registration mutations (Bhatt et al., 2025; Invariant Labs, 2025; Radosevich and Halloran, 2025). This project addresses that gap. By applying an ML classifier to the metadata features observable *after* registration — call-time description content, description-change flags, and session timing patterns — it tests whether the post-registration signal that rug-pull attacks necessarily generate is sufficient for detection. ETDI and schema-validation approaches address *containment* of detected attacks; this project addresses the *detection* of attacks that are not caught at registration. The two are complementary, not competing.
