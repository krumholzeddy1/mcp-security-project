# Chapter 2: Literature Review

## 2.1 The Emergence of Agentic AI and Tool-Calling Architectures

Large language models (LLMs) have evolved rapidly from systems that respond to isolated prompts into autonomous agents that plan, reason across multiple steps, and invoke external tools to complete tasks on a user's behalf. This shift from passive responders to active agents has been accompanied by the development of standardised protocols that allow models to discover and call tools provided by remote servers — a capability that dramatically extends what an LLM can accomplish but also introduces a new and largely uncharted attack surface.

Tool-calling architectures follow a common structural pattern: a client application hosts or communicates with an LLM, the LLM is presented with a catalogue of available tools at the start of a session, and the LLM autonomously selects and calls tools based on its interpretation of their declared metadata — principally their name, description, and parameter schema. The model never executes tool code directly; it constructs a structured call, and the client forwards it to the appropriate server. This indirection means that the model's behaviour is governed by what the metadata *says* the tool does, not by independent verification of what the tool *actually* does. The trust relationship between the model and the tool's declared description is therefore a critical security boundary.

---

## 2.2 The Model Context Protocol

Anthropic's Model Context Protocol (MCP) has emerged as the dominant open standard for this tool-calling layer. MCP defines a message-passing interface through which a client connects to one or more servers, requests a list of available tools via a `tools/list` call, and subsequently invokes tools via `tools/call`. Each tool is described by a name, a free-text description, and a JSON Schema defining its input parameters.

Hou, Zhao, Wang, and Wang (2025) provide a comprehensive survey of MCP's design landscape and security implications. They identify a structural weakness that is central to this project: MCP was designed to solve an interoperability problem — enabling any client to communicate with any server using a common protocol — and treats security as a secondary concern. The protocol has no built-in mechanism for re-validating the trust placed in a tool after the initial connection is established. Each layer in the pipeline — user, model, client, server — is assumed to trust the layer immediately behind it, but nothing re-checks that trust once a session is running. Hou et al. (2025) argue that this creates a situation where a compromised or malicious component several hops downstream can inject behaviour that is, from the model's perspective, indistinguishable from a legitimate instruction originating from the user.

A critical reading of Hou et al. (2025) requires preserving a distinction the paper does not always make explicit: that the vulnerabilities they describe are *structurally possible* given MCP's architecture, not that they are *commonly exploited* in practice. The paper is an architectural survey of a then-emerging protocol, not an empirical incident study. The degree to which these weaknesses are actively exploited in production deployments at the time of writing is unknown. This dissertation treats the Hou et al. analysis as establishing the *mechanism* of the attack surface, while relying on Radosevich and Halloran (2025) and Invariant Labs (2025) for evidence that attacks within that surface have been demonstrated in practice.

## 2.3 Tool-Poisoning Attacks

Tool poisoning exploits the model's reliance on tool metadata by embedding instruction-like text directly into the fields that the model treats as descriptive. Because LLMs are trained to follow instructions embedded in their context, text placed in a tool's name, description, or parameter schema can direct the model to perform actions that the user did not request and may not be aware of. This class of attack did not originate with MCP: Perez and Ribeiro (2022) established prompt injection as a general vulnerability of instruction-following language models — the observation that any text in the model's context window carrying imperative phrasing can override or redirect the model's behaviour. Greshake et al. (2023) extended this to *indirect* prompt injection, demonstrating that malicious instructions need not come from the user directly but can be embedded in any content the model reads, including external data sources and tool outputs. Tool poisoning via MCP metadata is a specific instantiation of this broader indirect-injection class: the injection vector is the tool description rather than a web page or document, but the underlying mechanism — the model processes the injected text as instruction rather than data — is the same.

Invariant Labs (2025) published the first detailed public demonstration of tool poisoning as a practical attack against deployed MCP systems. Their report documents working exploits in which tool descriptions contain hidden directives — including instructions to exfiltrate the contents of local configuration files, to relay the user's session credentials to a secondary endpoint, and to modify subsequent tool calls in ways that persist across the session. In all demonstrated cases, the tool appeared to function normally from the user's perspective: the visible output of the tool's invocation was unremarkable, while the injected behaviour operated silently in parallel. This source should be read with awareness that Invariant Labs is a commercial security vendor with a product in this space; the report has not been independently verified by a third party, and the company has a commercial interest in establishing the severity of the threat it is reporting. The Invariant Labs findings are treated here as corroborating evidence alongside the independently conducted audit of Radosevich and Halloran (2025), rather than as a standalone authority.

Radosevich and Halloran (2025) conducted a systematic safety audit of MCP deployments and confirmed that tool-poisoning vulnerabilities are not limited to contrived examples. Their audit identified multiple real-world MCP servers in which tool descriptions contained instruction-like text — sometimes introduced intentionally by server operators pursuing unauthorised data collection, and sometimes introduced inadvertently through misconfiguration or insecure default templates. They further demonstrate that injection via parameter *schema field names* (not only the description field) is also effective, because field names appear in the model's prompt alongside the description and are treated as semantically meaningful. This is the methodologically strongest of the MCP-specific sources reviewed here: a systematic audit across multiple deployments provides stronger evidence of prevalence than a single proof-of-concept demonstration. As an arXiv preprint it has not yet been confirmed as peer-reviewed, and the denominator — how many MCP deployments were audited, and how many were found clean — is not reported, which limits claims about the overall prevalence of the vulnerability.

## 2.4 The Rug-Pull Attack Pattern

A distinct variant that is more difficult to detect than direct poisoning is the delayed attack, commonly referred to as a rug-pull. Willison (2025) describes servers that register with honest, unmodified tool descriptions — passing any initial inspection or human review — and subsequently rewrite their tool definitions after the client has trusted them and established a session. From the protocol's perspective, nothing prevents a server from returning a different tool list in response to a `tools/list` call than it returned at the start of the session; the client has no mechanism for detecting or preventing this mutation.

Willison (2025) also identifies a related pattern: server impersonation, in which one server intercepts and responds on behalf of another server it was never meant to represent. Both patterns share the same structural property: the attack becomes visible only after the trust relationship has been established and the opportunity for initial inspection has passed. This places them outside the scope of any defence that checks a tool once, at the point of first registration.

A critical reading of this source is required. Willison (2025) is a practitioner blog post — a first-hand technical write-up with illustrative examples, not a peer-reviewed study, a systematic audit, or a controlled experiment. It has no methodology section, no data on how commonly the rug-pull pattern occurs in real deployments, and has not been externally verified. The rug-pull half of this dissertation's attack taxonomy rests entirely on this one non-peer-reviewed source. The tool-poisoning category has independent corroboration from both Invariant Labs (2025) and Radosevich and Halloran (2025); the rug-pull category does not. This asymmetry is acknowledged explicitly in the methodology (Section 3.3.1) and limitations (Section 5.2). The Willison account is retained as the foundational source for the rug-pull concept because the *mechanism* it describes — post-registration description mutation — is independently supported by the architectural analysis of Hou et al. (2025), who show that MCP's trust model structurally permits exactly this behaviour. The mechanism is therefore grounded, even if the empirical prevalence of the attack is not established.

The rug-pull attack is particularly significant in the context of automated or long-running agentic sessions, where a model may interact with a given tool many times over an extended period before a human operator reviews the session transcript. An attacker who controls a server can exploit the timing window between the initial connection — when the tool description is clean — and a later point in the session when monitoring attention may be lower.

## 2.5 Existing Defences and Their Limitations

Three categories of defence are in common use for MCP tool security, and all three share the structural limitation of checking a tool once rather than continuously.

**Schema validation** inspects a tool's declared JSON Schema at registration time, verifying that field types, required fields, and enumerated values conform to expected patterns. While this catches tools with obviously malformed schemas, it provides no protection against injection embedded in well-formed string fields — the description field accepts arbitrary text by design, and an injected directive in a `description` string passes schema validation trivially. Schema validation is also entirely registration-time, providing no visibility into changes that occur after the initial connection.

**OAuth-based access control**, exemplified by the Enhanced Tool Definition Interface (ETDI) proposed by Bhatt, Narajala, and Habler (2025), extends MCP with cryptographically signed tool definitions and policy-based access scoping. OAuth is an industry-standard authorisation framework that issues scoped access tokens controlling which actions a client is permitted to perform; ETDI applies this model to MCP tools by binding each tool's permitted actions to its declared identity at registration time, requiring that any invocation satisfy pre-approved scope constraints. This represents an improvement over schema validation in that it limits what a poisoned tool can accomplish even if the injection is not detected. However, ETDI does not address the rug-pull attack: if the server rewrites a tool's description after registration, the newly injected instructions may still fall within the originally approved scope, and the scope constraint does not detect the semantic change in the description itself. Bhatt et al. (2025) acknowledge this limitation, noting that ETDI is designed to prevent tool squatting (one tool masquerading as another at registration) rather than post-registration description mutation.

**Human review** — the practice of having a user or operator read tool descriptions before connecting — is the most common informal defence in current deployments. It is effective for detecting obvious injection in short, readable descriptions but does not scale to sessions with many tools, fails for descriptions in which injection is embedded in technical-looking text that a non-expert reviewer may not identify as anomalous, and provides no protection against rug-pull mutations that occur after the review has been completed.

The common failure mode across all three defences is temporal: each checks the state of a tool's metadata at a single point in time and does not revisit that check. Hou et al. (2025) characterise this as a structural property of MCP's trust model rather than a fixable parameter of any particular defence: the protocol provides no event notification when a server changes its tool definitions, and no session-level audit trail of description changes is maintained by the standard client implementation.

## 2.6 Machine-Learning Approaches to Security Anomaly Detection

The use of machine learning to detect security anomalies from behavioural metadata has a well-established history in network intrusion detection and malware classification. Ahmed et al. (2025) survey a decade of ML-based intrusion detection systems and identify a recurring pattern: anomaly-based methods consistently detect attack categories that signature-based methods miss by construction, because signatures require prior knowledge of the specific attack variant, whereas an anomaly model learns a representation of normal behaviour and flags deviations from it. Zhan et al. (2024) apply this principle specifically to adversarial attacks against AI-enabled systems, demonstrating that metadata features extracted from model interactions — request timing, payload structure, and response entropy — can distinguish adversarial from benign queries even when adversarial inputs are crafted to evade input-level filters. Together, these bodies of work establish the conceptual foundation for applying anomaly-based ML detection to MCP tool-call metadata.

The application of this precedent to MCP requires an assumption that deserves to be stated explicitly: *the transfer hypothesis* — that the statistical regularities (feature distributions, class separability, recall-precision trade-offs) observed in network intrusion detection and adversarial AI detection will be reproduced when those methods are applied to MCP tool-call metadata. This is a plausible hypothesis given the structural similarity of the problem (detecting deviations from a baseline of legitimate behaviour in session-level data), but it is a hypothesis, not a proven transfer. The degree to which insights from, for example, network packet metadata (large-scale, continuous, millisecond-resolution streams) generalise to MCP tool-call metadata (small-scale, sparse, session-level snapshots) is unknown. This dissertation tests the hypothesis empirically rather than assuming the transfer holds.

The common principle underlying both literatures is that malicious behaviour — even when it is deliberately designed to evade rule-based signatures — tends to leave statistical traces in observable features: timing distributions, payload lengths, entropy of content, and deviations from session-level baselines. Applied to the MCP tool-poisoning context, this principle suggests that attacks may be detectable from metadata features — description lengths, entropy values, keyword-hit counts, and the pattern of changes across the session — even when the attack text itself is crafted to evade a specific keyword list. Gradient-boosted tree classifiers are a well-established choice for this kind of tabular, heterogeneous feature set: they handle mixed feature types without preprocessing, provide interpretable feature importance scores that allow post-hoc analysis of which features drive predictions, and are competitive with more complex architectures on structured data of moderate size (Chen and Guestrin, 2016). A critical limitation of Chen and Guestrin (2016) as a reference for this project is scale: their benchmark involves datasets orders of magnitude larger than the 600-session synthetic corpus used here. The applicability of their scale-dependent conclusions to a small synthetic dataset is acknowledged as a limitation of this study (Section 5.2).

No prior published work has applied machine-learning-based anomaly detection specifically to MCP tool-call metadata for the purpose of detecting post-registration description changes. The closest adjacent work — Bhatt et al. (2025) and Hou et al. (2025) — proposes and analyses registration-time defences, leaving the post-registration detection problem unaddressed. This dissertation does not compete with those defences; ETDI and schema-validation approaches address the *containment* of attacks that are detected, while this project addresses the *detection* of attacks that are not caught at registration. As Bhatt et al. (2025) acknowledge, ETDI does not address post-registration description mutation; a detection layer and a containment layer are complementary rather than substitutable.

## 2.7 Research Gap

The literature establishes two complementary facts. First, rug-pull attacks against MCP tools are a documented, practical threat that exploits a structural gap in how MCP manages trust across the lifetime of a session (Willison, 2025; Hou et al., 2025). Second, all defences that have been proposed or deployed to date check tool metadata at a single point — registration — and are therefore structurally unable to detect mutations that occur after that point, regardless of how sophisticated the checking logic is (Bhatt et al., 2025; Invariant Labs, 2025; Radosevich and Halloran, 2025).

This project addresses the gap between these two facts. By applying a machine-learning classifier to the metadata features observable *after* tool registration — including call-time description content, description-change flags, and session timing patterns — it tests whether the post-registration signal that rug-pull attacks necessarily generate can be exploited for detection. The research question is therefore not whether existing defences can be improved by tuning their parameters, but whether a fundamentally different observability window — one that extends beyond registration time — produces a qualitatively different detection capability for the attack class that existing defences cannot reach.
