## Project Purpose

PhD dissertation research (CO4011, UCLan/RKC Lancashire) investigating ML-based detection of **tool-poisoning attacks** in Model Context Protocol (MCP) agentic AI systems. The central research question: can a classifier trained on tool-call *metadata features* detect rug-pull attacks that a registration-time keyword/schema validator structurally cannot see?

## Pipeline Execution Order

The pipeline stages must run in sequence — each stage depends on outputs from the prior one:

```bash
python -m corpus.generate_corpus       # → data/corpus.csv  (600 synthetic sessions)
python -m baseline.schema_validator    # → data/baseline_results.csv
python -m detection.train_model        # → data/detector_model.joblib, data/model_test_results.csv
python -m evaluation.evaluate          # → data/evaluation_summary.csv
```

All commands must be run from the repo root with the virtualenv active.

## Architecture

### Data Flow

`corpus/generate_corpus.py` → `data/corpus.csv` → `baseline/schema_validator.py` and `detection/train_model.py` → `evaluation/evaluate.py` compares both methods on the same test split.

### Three Session Classes

The synthetic corpus has three balanced classes (200 sessions each by default, `random.seed(42)`):

- **benign** — normal registration and calls, no attack
- **poisoned** — description contains an injection fragment at *registration* time (visible to baseline)
- **rugpull** — description starts clean, mutates mid-session (invisible to baseline by construction — registration keyword hits always = 0)

### Feature Set

Detection operates on **11 metadata features only** — not raw description text. Key features: `num_schema_fields`, `reg_description_length`, `reg_description_entropy`, `reg_suspicious_keyword_hits`, `call_description_length`, `call_description_entropy`, `call_suspicious_keyword_hits`, `description_changed_after_registration`, `time_since_registration_s`, `call_position_in_session`, `num_calls_in_session`.

### Baseline vs ML

- **Baseline** (`baseline/schema_validator.py`): flags if `reg_suspicious_keyword_hits >= 1`. Structurally blind to rug-pulls — always 0% recall on that class.
- **ML detector** (`detection/train_model.py`): `GradientBoostingClassifier` on all 11 features, 70/30 stratified split. Has access to call-time and description-change features, enabling rug-pull detection.

### Supporting Components

- **`server/tool_definitions.py`** — shared `ToolSpec` dataclass and `TOOL_CATALOG` (5 benign tools with associated `poison_fragments`). Imported by the corpus generator; this is the shared data model.
- **`server/testbed_server.py`** — real `FastMCP` server over stdio, for demos and supervisor walkthroughs only. Not part of the training pipeline.
- **`client/testbed_client.py`** — async MCP client for manual round-trip demos; requires the testbed server running externally.

## Key Design Decisions

- The `data/` directory holds pipeline *outputs* (`.csv` files, `.joblib` model) — these are regenerated by running the pipeline, not committed as source.
- The corpus is deliberately **too clean/separable** as of early weeks — adding noise to `generate_corpus.py` (weeks 4–5) is a known dissertation task to make results more credible.
- Modules use `sys.path.insert(0, ...)` in their entry points to handle repo-root imports; all packages have empty `__init__.py` files.
- No version constraints on any dependency in `requirements.txt` — pin versions before final submission to ensure reproducibility.
